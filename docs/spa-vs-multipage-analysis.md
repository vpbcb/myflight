# MyFlight: переходить ли с multipage на single-page — анализ и рекомендация

## Context

Пользователь спросил, есть ли смысл переводить PWA MyFlight с нескольких HTML-страниц на
одну (SPA). Поводом стали недавние проблемы, характерные для multipage-архитектуры:
- один и тот же код фиксации высоты (`MyFlightViewportLock`) пришлось править в шести копиях;
- клавиатура дёргалась из-за пересчётов высоты при каждой загрузке страницы;
- состояние между страницами передаётся через `localStorage` (например, борт и экипаж
  с главной в MyLoad).

## Текущее состояние (замеры)

- **Шесть самостоятельных страниц**, всего ~23 тыс. строк:
  - `index.html` — 144 КБ
  - `mynpa.html` — 410 КБ (из них 277 КБ инлайн-JS)
  - `mywind.html` — 122 КБ
  - `myfuel.html` — 102 КБ
  - `mypath.html` — 94 КБ
  - `myshift.html` — 92 КБ
- **Переходы — обычные ссылки** `<a href="./mywind.html">`. Service worker отдаёт навигации
  из прекэша (`appShellResponse` в `sw.source.js:210`). Страница открывается без сети и быстро,
  но каждый переход — полная перезагрузка.
- **Всё построено на глобальной области видимости.** На страницах ~400 инлайн-обработчиков
  (`onclick="calculateAll()"` и т. п.), которые обращаются к глобальным функциям.
- **Конфликты при объединении в одну страницу:**
  - 20 имён глобальных функций совпадают на разных страницах, с разной реализацией:
    `calculate`, `openKeypad`, `kpPress`, `saveAppState`, `loadAppState`, `fillInfoModal`, …
  - 19 `id` элементов повторяются на разных страницах;
  - 8 CSS-переменных `:root` на разных страницах означают разное: `--accent`, `--bg`, `--card`,
    `--text-main`, …
  - CSS каждой страницы (24–92 КБ) написан без изоляции.
- **Общее состояние небольшое**, 9 ключей `localStorage`: `hub_theme`, `fuelApp_data`,
  `rwyWind_state`, `myPath_state`, … Смена темы синхронизируется событием `storage`.
- **Тесты привязаны к файлам страниц:** 26 из 30 читают конкретные `*.html`.
- **Офлайн-модель** (прекэш сборки, закрепление сборки за клиентом, `offline-build` meta)
  рассчитана на навигацию по страницам.

## Оценка

**Что дала бы SPA**
- Плавные переходы без перезагрузки и без мигания.
- Один экземпляр общего кода: фиксация высоты, тема, навигация.
- Состояние в памяти вместо `localStorage`.
- Фиксация высоты инициализируется один раз, а не при каждом переходе.

**Чего это стоит**
- По сути переписать приложение. Все 400 инлайн-обработчиков, 20 конфликтующих функций,
  19 id и CSS пришлось бы изолировать по разделам.
- `mynpa` (410 КБ) нужно было бы загружать лениво, иначе старт станет заметно медленнее.
- Пришлось бы переделать офлайн-модель service worker и почти все тесты.
- Большой риск регрессий в инструменте, по которому пилот считает центровку, ветер и глиссаду.
- В SPA сбой состояния (зависшая высота окна, утечка обработчиков) живёт до перезапуска
  приложения. Сейчас любой переход между страницами сбрасывает его. Для iOS/Android PWA
  с их проблемами клавиатуры и высоты окна это реальное преимущество текущей схемы.

**Главное:** почти все выгоды SPA можно получить гораздо дешевле, не меняя архитектуру.
- Дублирование убирается выносом общего кода в общие файлы.
- Плавность переходов даёт нативный cross-document View Transitions API:
  `@view-transition { navigation: auto; }`. Он поддерживается в Chrome Android 126+ и Safari
  iOS 18.2+, а на старых версиях браузер просто переходит без анимации.
- Скорость переходов уже обеспечивает прекэш service worker.

## Рекомендация

Переходить на SPA сейчас **нет смысла**: затраты и риск несоразмерны выгоде.
Вместо этого — два точечных шага.

1. **Вынести общий код в общие файлы.**
   - `viewport-lock.js` — блок `MyFlightViewportLock` сейчас скопирован в 6 страниц
     (например, `myfuel.html` ~596–760); в `index.html` у него два локальных отличия, их
     оставить параметром или отдельной веткой.
   - Если он так же продублирован, общий инлайн-скрипт применения темы (`hub_theme`).
   - Подключить файлы в `<head>` синхронно, как сейчас работают инлайн-скрипты, чтобы не было
     мигания.
   - Добавить файлы в `scripts/build-offline.cjs` (прекэш) и `scripts/check-syntax.cjs`.
   - Тест `tests/viewport-lock-keyboard.test.js` переключить на загрузку `viewport-lock.js`
     и проверку, что все 6 страниц его подключают.
2. **Плавные переходы между страницами.**
   - Добавить `@view-transition { navigation: auto; }` в общий `bottom-navigation.css`
     (он уже подключён на всех страницах).
   - Убедиться, что фон `html`/`body` задан до первой отрисовки в обеих темах, чтобы не было
     белой вспышки.
   - Нижнюю панель пометить `view-transition-name`, чтобы при переходе она оставалась на месте.

К SPA стоит вернуться, только если появится требование, которое без неё не решается: общее
живое состояние между экранами (например, данные рейса онлайн), анимации внутри одного
экрана или обёртка в нативное приложение.

## Проверка (для шагов 1–2)

- `npm run lint`, `npm test`: все тесты зелёные.
- `npm run bump:cache`, `npm run build`.
- Локально на 5174 и на телефоне (Android и iOS, установленный PWA):
  - переходы Главная ↔ MyLoad ↔ MyWind ↔ MyPath проходят с анимацией и без белой вспышки
    в обеих темах;
  - нижняя панель при переходе не прыгает;
  - клавиатура на MyLoad открывается ровно, в том числе сразу после перехода;
  - офлайн (режим полёта): все страницы открываются.

## Дополнение: задержка при переходе между страницами

Пример: нажатие MyPath в MyWind открывает страницу не сразу, а с заметной задержкой.

### Рекомендации выше эту проблему не решают

- **Вынос общего кода в общие файлы** убирает только дублирование. На скорость открытия
  страницы он не влияет.
- **View Transitions** лишь анимирует смену экрана. Анимация стартует, когда новая страница
  уже готова, поэтому ожидание остаётся.

### Откуда берётся задержка (гипотезы, не замерено)

Обработчик кнопки MyPath в MyWind (`clickPathSwitch`) переход не задерживает.

1. **Service worker делает несколько асинхронных шагов до ответа** (`appShellResponse` в
   `sw.source.js`):
   - `completeBuilds()` перебирает сохранённые сборки кэша;
   - `cache.match` ищет страницу;
   - `pinClient` закрепляет сборку за вкладкой, то есть пишет в кэш, и это ждёт до отдачи
     страницы.

   Каждый скрипт и CSS страницы потом проходит `cacheFirst` → `matchAppCaches` с поиском
   закреплённой сборки.
2. **Холодный старт service worker.** Android выгружает его в простое, и повторный запуск
   добавляет время ещё до первого шага.
3. **Сама загрузка страницы:** разбор ~94 КБ HTML, инлайн-скриптов и работа в
   `window.onload` у MyPath (`mypath.html`, ~стр. 2277).

### Порядок действий

1. **Замер.** Снять тайминги перехода MyWind → MyPath на телефоне в установленном PWA —
   пошагово описано в разделе «Замер задержки перехода: пошагово» ниже.
2. **Ускорить путь service worker при навигации** (если замер покажет, что основное время
   уходит на него):
   - отдавать страницу сразу после `cache.match`, а `pinClient` выполнять после ответа
     через `event.waitUntil`;
   - держать результат `completeBuilds()` и закреплённую сборку клиента в памяти, а не
     перечитывать из Cache Storage на каждый запрос.

   Изоляцию сборок (`docs/offline-isolation.md`) при этом не нарушать: закрепление должно
   произойти до того, как страница запросит свои ресурсы.
3. **Предзагрузка соседних страниц** через Speculation Rules
   (`<script type="speculationrules">`, prefetch/prerender). Например, MyPath можно
   подготовить, пока открыт MyWind, и тогда переход будет почти мгновенным. Работает в Chrome
   на Android, на iOS правила игнорируются, и ничего не ломается. Совместимость с
   service worker и закреплением сборки нужно проверить отдельно.
4. **Ускорить старт страниц** (если замер покажет, что время уходит на скрипты): отложить
   некритичную инициализацию до первой отрисовки, тяжёлые данные грузить лениво.

### Замер задержки перехода: пошагово

**A. Подготовка телефона (один раз)**
1. Настройки → О телефоне → 7 раз нажать «Номер сборки». Появятся «Параметры разработчика».
2. Параметры разработчика → включить «Отладка по USB».
3. Подключить телефон кабелем к ПК. На телефоне разрешить отладку для этого компьютера
   (запрос с RSA-ключом, отметить «Всегда разрешать»).
4. На Windows может понадобиться USB-драйвер производителя (Samsung, Xiaomi) или Google USB
   Driver, если телефон не виден.

**B. Подключение DevTools**
1. На ПК в Chrome открыть `chrome://inspect/#devices` и включить «Discover USB devices».
   Телефон появится в списке, под ним открытые страницы установленного PWA MyFlight
   (адрес `…/myflight…/mywind.html`) и отдельной строкой service worker.
2. Если Chrome пишет, что отладка запрещена политикой, попробовать Edge (`edge://inspect`)
   или другой компьютер без корпоративных политик.
3. Нажать «inspect» у страницы MyWind.

**C. Что снять (три замера, каждый — 3–5 повторов)**

*Замер 1 — Network, главный:*
1. Во вкладке Network включить «Preserve log», «Disable cache» не включать.
2. На телефоне нажать MyPath.
3. Выбрать запрос `mypath.html` (тип document, пометка «ServiceWorker») → вкладка Timing.
   Записать:
   - «ServiceWorker Startup» — холодный запуск service worker;
   - «ServiceWorker respondWith» — время работы `appShellResponse`;
   - общее время запроса.
4. Для `app.js`, `offline-client.js`, `bottom-navigation.css` записать общее время.
5. Повторить сразу (service worker тёплый) и после 1–2 минут простоя (Android выгрузит
   service worker, будет холодный старт).

*Замер 2 — Navigation Timing в консоли:*
После открытия MyPath нажать «inspect» уже у страницы MyPath и выполнить в Console:

```js
const n = performance.getEntriesByType('navigation')[0];
const paint = Object.fromEntries(performance.getEntriesByType('paint').map(p => [p.name, Math.round(p.startTime)]));
console.table({
  'SW стартовал (workerStart)': Math.round(n.workerStart),
  'Ответ SW (responseStart)': Math.round(n.responseStart),
  'HTML получен (responseEnd)': Math.round(n.responseEnd),
  'DOM готов (domContentLoadedEventEnd)': Math.round(n.domContentLoadedEventEnd),
  'load (loadEventEnd)': Math.round(n.loadEventEnd),
  'Первая отрисовка': paint['first-contentful-paint'] ?? paint['first-paint']
});
```

Все значения в мс от начала навигации. Время выгрузки MyWind, до начала навигации, сюда
не входит.

*Замер 3 — Performance (если замеры 1–2 указывают на скрипты страницы):*
1. В DevTools страницы MyWind открыть вкладку Performance → Record.
2. На телефоне нажать MyPath, дождаться открытия, нажать Stop.
3. Сохранить профиль через «Save profile» (`.json`).

**D. Как читать результат**
- Большие «ServiceWorker Startup» или `workerStart` — холодный старт service worker.
  Лечится предзагрузкой (Speculation Rules) или SPA.
- Большой «respondWith» или `responseStart − workerStart` — медленный путь навигации в
  service worker. Это шаг 2 «Порядка действий».
- Большие `domContentLoadedEventEnd − responseEnd` или время до первой отрисовки — тяжёлые
  скрипты или разбор страницы. Это шаг 4.
- Всё быстрое (< 150 мс), а визуально задержка есть — время уходит на выгрузку MyWind или
  нажатие срабатывает не сразу. Проверить обработчики нажатия и `pagehide`.

**E. Что прислать для анализа**
- Скриншоты вкладки Timing для `mypath.html`: тёплый и холодный service worker.
- Вывод `console.table` (скриншот или текст).
- Файл профиля Performance, если снимался.
- Модель телефона и версию Chrome (`chrome://version` на телефоне).

### Как это меняет вывод

Если задержка переходов — главная проблема для пользователя, это основной аргумент в
пользу SPA: переключение экранов внутри одной страницы мгновенное. Но сначала стоит пройти
шаги 1–3 выше: они дешевле и не несут рисков переписывания. К SPA возвращаться, только если
после оптимизации service worker и предзагрузки задержка останется заметной.
